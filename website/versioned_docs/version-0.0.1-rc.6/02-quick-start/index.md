# Quick Start

This is the complete end-to-end walkthrough for `@agent-assembly/sdk`: **install →
connect → allow → deny → approval → read the errors → observe in the dashboard →
tune a policy and re-run → explore the examples**. Every command and code block on
this page runs against the published `@agent-assembly/sdk@0.0.1-rc.6` and the real
`aa-gateway` image — where a step is genuinely blocked at this pre-release, the page
says so plainly rather than faking a working flow.

This SDK is the **in-process (SDK) layer** of Agent Assembly's three-layer model. It
wraps your agent's tools and consults a policy decision *before* each tool runs. The
authoritative decision is made by an Agent Assembly **gateway**; the SDK is the fast
path that carries the call to it.

## 2. Connect — how enforcement actually works

Before any code: understand **what makes a policy decision real**, because the naive
configuration governs nothing. There are two paths, and this page uses both:

- **Path A — self-contained local demo (no gateway).** You supply your own
  `gatewayClient` that evaluates a small policy in-process. Nothing is installed or run
  beyond the SDK; it is the fastest way to *see the allow/deny shape*. Sections 3–6 use
  this path — it's exactly what the runnable framework
  [examples](https://github.com/ai-agent-assembly/examples/tree/HEAD/node) do.
- **Path B — real gateway-authoritative enforcement.** A running `aa-runtime` +
  `aa-gateway` make the decision from a loaded policy file. Sections 7–8 use this path.

:::danger[The default configuration enforces nothing]
A copy-paste of `initAssembly({ gatewayUrl, agentId, langchain: { tools } })` with **no
`mode`** governs nothing. The default `mode: "auto"` routes every tool through an
**allow-all no-op client** — `check()` never denies. To make the SDK route a check
through a real decision you must set **both**:

```ts
await initAssembly({
  agentId: "demo",
  mode: "napi-inprocess",     // the only mode whose check() consults the native runtime
  enforcementMode: "enforce", // a DENY blocks the tool; without this a deny is not enforced
  gatewayUrl: "/tmp/aa-runtime-demo.sock", // see the gatewayUrl note below
  langchain: { tools }
});
```

…and have an `aa-runtime` + `aa-gateway` reachable (Path B). This is the enforcing
configuration; the SDK will otherwise fail-open by design.
:::

:::note[`gatewayUrl` means different things in different modes]
`gatewayUrl` is **overloaded**. In `napi-inprocess` mode it is passed straight to the
native client as the **`aa-runtime` Unix-domain-socket path**, e.g.
`/tmp/aa-runtime-<agentId>.sock` (you can also set `AA_RUNTIME_SOCKET`) — an `http://…`
URL is *invalid* here and produces a native connect error. In the URL-based paths it is
an HTTP base such as `http://localhost:7391`. Agent **registration** is a separate,
direct SDK → gateway gRPC call that uses `AA_GATEWAY_ENDPOINT` (default
`127.0.0.1:50051`), not `gatewayUrl`. So the same field addresses a socket for checks
and a URL elsewhere — set it to match your `mode`.
:::

See [Configuration](../05-configuration/index.md) for the full resolution order
(`AA_GATEWAY_URL`, the config file, and the local default).

## 3. Wire governance into your agent

`withAssembly` wraps a map of tools so the policy is consulted before each one runs: an
allowed call executes normally, a denied call throws a `PolicyViolationError` and the
tool body never runs. Pick your framework — each tab is the governance-wiring excerpt
from that framework's runnable
[example](https://github.com/ai-agent-assembly/examples/tree/HEAD/node), vendored into
this repo and kept in lock-step by a CI drift check. Copy the full, runnable script —
imports, tools, and the agent run — from the linked example; the slice below is just the
part that wires in governance.

Here `createPolicyGatewayClient()` is the example's **local, in-process policy client**
(Path A): it evaluates a small allow/deny rule set with no gateway running, so these
snippets run offline. **LangChain.js** is the validated path; the rest are experimental.
The excerpts are ESM / TypeScript; under CommonJS, swap the import for
`const { withAssembly } = require("@agent-assembly/sdk")`.

## 3a. An allowed call

An allowed tool runs normally and returns its result. Using the LangChain.js example's
policy (`get_weather` is allowed):

```ts
const result = await tools.get_weather.execute({ city: "Tokyo" });
// → runs normally; the policy recorded an allow event
console.log(result);
```

## 4. A denied call

A denied tool **throws before its body runs** — the deny is the whole point. In the same
example, `delete_file` is denied:

```ts
import { PolicyViolationError } from "@agent-assembly/sdk";

try {
  await tools.delete_file.execute({ path: "/etc/hosts" });
} catch (err) {
  if (err instanceof PolicyViolationError) {
    // err.message includes the tool name and the gateway's reason;
    // the delete_file body never executed.
    console.error("blocked:", err.message);
  } else {
    throw err;
  }
}
```

## 5. Approval (human-in-the-loop) — current status

A policy can hold a call for a human to approve instead of a flat allow/deny (see
`requires_approval_if` in the policy schema in §8).

:::caution[Approval is not exercisable from the Node SDK at rc.6]
The Node SDK does **not** yet wire a real approval channel (poll/stream) —
`waitForApproval` is a stub. Under `enforce`, a tool that resolves to *approval-required*
**fail-closes to a deny** with a reason like `approval required but no approval channel
is configured`, surfaced to your caller as a `PolicyViolationError`. So in Node today you
observe **deny**, not a pending/approved outcome. This is an accurate current limitation,
not a bug in your wiring; approval decisions are still visible to operators in the
dashboard's audit trail (§7). Track it in AAASM-4997.
:::

## 6. Interpret the outcomes

| Outcome | What you see in code |
|---|---|
| **Allow** | The tool runs and returns its value; an allow event is recorded. |
| **Deny** | The wrapped call **rejects** with `PolicyViolationError` (tool name + gateway reason); the tool body never runs. |
| **Approval required** | On Node at rc.6 this **resolves to a deny** (see §5) — a `PolicyViolationError` whose reason mentions the missing approval channel. |

If you want to watch what *would* be blocked without actually blocking it while you tune
policy, register the agent in **observe** mode — actions proceed and violations are
recorded as shadow events:

```ts
const ctx = await initAssembly({
  agentId: "demo",
  enforcementMode: "observe", // dry-run: actions proceed, violations recorded as shadow events
  langchain: { tools: { searchWeb } }
});
```

## 8. Tune a policy and re-run

To change what the gateway decides, edit its **policy** and re-run. This is the real,
gateway-authoritative path (Path B): a running `aa-runtime` + `aa-gateway` load a policy
file and decide per tool. The fully wired, runnable stack lives in the
[`live-core-enforcement` example](https://github.com/ai-agent-assembly/examples/tree/HEAD/scenarios/live-core-enforcement)
(`docker compose` brings up `aa-gateway` + `aa-runtime`, then runs an agent).

The gateway loads a **section-based** policy. Here is a real policy the gateway accepts —
`read_file` is allowed, `delete_file` is denied:

```yaml
# policy.yaml — section-based schema (the schema the gateway actually loads)
approval_timeout_secs: 300

tools:
  read_file:
    allow: true
    limit_per_hour: 50
  delete_file:
    allow: false            # ← flip to `true`, reload, and delete_file stops being denied

data:
  sensitive_patterns:
    - "sk-[A-Za-z0-9]{32,}"

budget:
  daily_limit_usd: 5.00
```

Change `delete_file: { allow: false }` to `allow: true`, restart the stack, and the same
call that was denied now runs — that is policy tuning end-to-end.

:::warning[Use the section-based schema — the rule-list schema is rejected]
The gateway loads a **section-based** document. The valid top-level keys are exactly:
`version`, `scope`, `network`, `schedule`, `budget`, `data`, `tools`, `capabilities`,
`approval_timeout_secs`, `approval`. Per-tool approval is expressed with
`requires_approval_if: "<expr>"` (an expression over `path`, `url`, etc.), **not** an
`action: approval_required`.

An older **rule-list** shape (top-level `agent_id`, `rules: [{tool, action, reason}]`,
`default_action`) is **refused** by the rc.6 gateway to avoid an allow-all fallback —
loading it errors with `unsupported rule-list policy schema (top-level 'rules:')`.
Verified by loading both shapes into `ghcr.io/ai-agent-assembly/aa-gateway:v0.0.1-rc.6`.
See the monorepo's `schemas/examples/balanced.yaml` for a full annotated example.
:::
